# Draft Email: one-click pitch email generation from insights

## Problem Statement

Sales users generate strategic insights briefs on the `/app` page, then must manually write a pitch email to the advertiser from scratch. This is time-consuming, inconsistent across the team, and the quality of the email depends entirely on the individual salesperson's writing ability. The insights brief contains everything needed for a compelling pitch, but translating a detailed analytical document into a short, punchy sales email is a separate skill that not every salesperson excels at.

## Solution

Add a "Draft Email" button that appears after insights are generated. One click produces a short, meeting-focused pitch email (with subject line) addressed to the advertiser, ready to copy into an email client. The email is generated by GPT-4o-mini using the full insights brief as context.

To ensure each salesperson's emails sound like *them* rather than a generic AI, users can store 1-5 sample emails they've previously sent. The LLM uses these samples to match the user's personal writing style and tone. Samples are stored persistently per user — upload once, reuse forever.

The onboarding flow is built into the button itself: first-time users who click "Draft Email" are guided through pasting their first sample email before the draft is generated, making setup seamless and discoverable.

## User Stories

1. As a salesperson, I want to generate a pitch email from my insights brief with one click, so that I can reach out to advertisers faster.
2. As a salesperson, I want the generated email to be short and focused on getting a meeting, so that it matches how effective sales outreach actually works.
3. As a salesperson, I want the email to include a subject line, so that I have a complete draft ready to paste into my email client.
4. As a salesperson, I want the email to reference the specific advertiser, topic, and KPI from my brief, so that the pitch feels personalised and relevant.
5. As a salesperson, I want the email to use a `[Name]` placeholder for the recipient, so that I can fill in the contact's name after pasting.
6. As a salesperson, I want to store sample emails I've sent in the past, so that the LLM can match my personal writing style.
7. As a salesperson, I want to paste sample emails as plain text (not upload files), so that setup is quick and I can control exactly what text is used.
8. As a salesperson, I want to store between 1 and 5 sample emails, so that the LLM has enough signal without being overwhelmed.
9. As a first-time user, I want to be guided through adding my first sample email when I click "Draft Email", so that I don't have to find a separate settings page before the feature works.
10. As a salesperson, I want to copy the generated email to my clipboard with one click, so that I can paste it straight into Outlook/Gmail.
11. As a salesperson, I want to regenerate the email draft if the first version doesn't land, so that I can get a different take without re-running the full insights pipeline.
12. As a salesperson, I want to see how many sample emails I've stored and manage them (add/remove), so that I can keep my style samples up to date.
13. As a salesperson, I want to access sample management via a link near the "Draft Email" button (e.g. "Writing style: 3 samples"), so that I don't have to navigate to a separate page.
14. As a salesperson, I want the email draft to appear in a modal overlay, so that I can still see my insights brief in the background.
15. As a salesperson, I want the modal to show a loading state while the email is being generated, so that I know the system is working.
16. As an unauthenticated user, I should not be able to access the draft email or writing samples endpoints, so that user data is protected.
17. As a salesperson, I should only be able to view and delete my own writing samples, so that other users' data is private.
18. As a salesperson, I want the "Draft Email" button to only appear after insights have been generated, so that the UI isn't cluttered before there's content to draft from.

## Implementation Decisions

### Backend

**Email samples storage**
- New `email_samples` table in the existing `users.db` SQLite database: `(id INTEGER PRIMARY KEY, user_id INTEGER NOT NULL, content TEXT NOT NULL, created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, FOREIGN KEY (user_id) REFERENCES users(id))`
- Maximum 5 samples per user, enforced at the database module level
- CRUD functions added to the existing database module: `create_email_sample()`, `get_email_samples()`, `delete_email_sample()`

**Email samples API**
- New API router with three endpoints:
  - `GET /api/email-samples` ��� returns list of current user's samples
  - `POST /api/email-samples` — add a sample (validates non-empty content, enforces max 5 limit)
  - `DELETE /api/email-samples/{id}` — delete a sample (validates ownership — user can only delete their own)
- All endpoints protected by the existing `get_current_user` JWT dependency

**Email drafter**
- New module with a single entry point: `draft_email(brief_content, topic, advertiser, kpi, writing_samples) -> {subject, body}`
- Uses GPT-4o-mini (configured via a new `EMAIL_DRAFT_MODEL` constant in config, defaulting to `"gpt-4o-mini"`)
- Prompt architecture:
  - System prompt: defines role as a sales email copywriter, instructs to write a short 3-5 paragraph pitch email to get a meeting booked, include a subject line, use `[Name]` placeholder for recipient
  - Conditionally includes writing style section: if samples are provided, instructs LLM to match the tone, sentence structure, greeting style, and sign-off patterns from the samples
  - User prompt: includes the full insights brief content plus the explicit topic, advertiser, and KPI values
- Response parsed to extract subject line and body separately

**Draft email endpoint**
- `POST /api/draft-email` on the existing FastAPI app
- Accepts: `{ content: string, topic: string, advertiser: string, kpi: string }`
- Server-side: fetches the authenticated user's writing samples from the DB, passes everything to `draft_email()`, returns `{ subject: string, body: string }`
- Protected by `get_current_user`

### Frontend

**Draft Email Modal**
- New modal component with two modes:
  - *Onboarding mode*: shown when user has no samples. Contains a text area to paste their first sample email, a "Save & Draft" button that stores the sample then immediately generates the draft
  - *Draft mode*: shown when samples exist. Opens with a loading spinner, then displays the generated subject line and email body. Includes "Copy to clipboard" and "Regenerate" buttons
- "Copy to clipboard" copies both subject and body as formatted text
- "Regenerate" makes another API call with the same inputs

**Writing Samples Modal**
- Separate modal for managing samples, opened via a "Writing style: N samples" link near the Draft Email button
- Lists existing samples with truncated preview and delete button for each
- Text area to add a new sample with character count guidance
- Shows "N of 5" count

**Insights page integration**
- "Draft Email" button rendered below the results section (after all collapsible panels), only visible when `result` is set
- "Writing style: N samples" link rendered next to/below the button
- Page fetches the user's sample count when results are displayed, to determine which modal mode to use when the button is clicked

### Analytics
- Track events via existing `useAnalytics()` hook:
  - `"Draft Email Clicked"` — with `{ has_samples: boolean, sample_count: number }`
  - `"Draft Email Generated"` — with `{ topic, advertiser, kpi, sample_count, duration_ms }`
  - `"Draft Email Copied"` — fired on clipboard copy
  - `"Draft Email Regenerated"`
  - `"Writing Sample Added"` / `"Writing Sample Deleted"`

## Testing Decisions

Tests should verify external behaviour through the module's public interface, not implementation details. Mock external dependencies (OpenAI API, database connections) at the boundary.

**Modules to test:**

1. **Email samples database functions** (pytest, aiosqlite)
   - CRUD operations: create, list, delete
   - Max 5 limit enforcement (creating a 6th should fail)
   - Ownership isolation (user A cannot see/delete user B's samples)
   - Edge cases: empty content rejection, deleting non-existent sample
   - *Prior art*: follows the same async SQLite pattern as the existing user database module

2. **Email drafter module** (pytest, mocked OpenAI)
   - Prompt assembly: verify the prompt includes topic, advertiser, KPI, and brief content
   - Style section: verify writing samples are included in the prompt when provided, omitted when empty
   - Model selection: verify GPT-4o-mini is used (not GPT-4o)
   - Response parsing: verify subject and body are correctly extracted from LLM output
   - *Prior art*: similar pattern to how `synthesiser.py` calls OpenAI — mock at the client boundary

3. **Email samples API endpoints** (pytest, FastAPI TestClient)
   - Auth gating: all three endpoints return 401 without a valid JWT
   - POST validation: rejects empty content, rejects when at max capacity (5)
   - DELETE ownership: returns 404 when trying to delete another user's sample
   - Happy path: create -> list -> delete lifecycle

## Out of Scope

- **Section selection before drafting** — the LLM receives the full brief and decides what's most compelling. No UI for cherry-picking sections.
- **Editable draft in the modal** — users edit in their email client after copying. The modal is read-only.
- **File upload for samples** — email file formats (`.eml`, `.msg`) require complex parsing. Copy-paste only.
- **Recipient name input** — the draft uses a `[Name]` placeholder. Users fill it in after pasting.
- **Full-pitch long-form email variant** — only the short, get-the-meeting style is supported. A "full pitch" option may come later.
- **Email sending** — Prism Data Vault generates the draft; the user sends it from their own email client.
- **Sample email analysis/feedback** — no UI telling users whether their samples are "good enough" for style matching.

## Further Notes

- The email drafter prompt should explicitly instruct the LLM *not* to include every section from the brief — the email's job is to hook interest with 2-3 compelling data points and secure a meeting, not to reproduce the brief.
- GPT-4o-mini was chosen over GPT-4o for this task because email drafting is a simpler transformation (distill + restyle) that doesn't require strong reasoning. This gives faster modal response times and lower cost per draft. The model can be upgraded via config if quality proves insufficient.
- The `[Name]` placeholder convention is standard in sales email tooling and immediately signals to the user where to personalise.
- Writing samples are stored as plain text. No HTML, no rich formatting. This keeps the DB simple and ensures clean input to the LLM prompt.
- The onboarding modal flow (click "Draft Email" -> guided to paste first sample -> draft generates) is designed so that users discover the style feature at the moment of highest intent, not through a separate settings page they'd need to find proactively.
